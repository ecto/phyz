# phyz Benchmarks

phyz's README makes performance claims — "GPU-accelerated", "thousands of
parallel environments", "analytical derivatives for free". This document is the
evidence for and against them.

It is written to be useful to someone deciding whether to use phyz, which means
it reports where phyz loses as plainly as where it wins. There are losses here.
One of them contradicts a README claim.

Generated by [`crates/phyz-bench`](crates/phyz-bench/). Reproduce with:

```bash
make bench
```

---

## Summary

| Claim | Verdict |
|---|---|
| Fast single-sim rigid body dynamics | **Holds.** 4.1 M steps/s on a pendulum, 229 k on a 14-DOF ant; marginally faster than Rapier (1.0–1.1×) on reduced-coordinate chains at matched precision. |
| GPU-accelerated batch simulation | **Holds above batch ~128.** 36× a CPU thread at batch 4096. Below batch 128 the GPU path is *slower* than one CPU core — at batch 1 it is 100× slower. |
| "Thousands of parallel environments" | **Holds.** 16 384 environments run at 7.8 M env-steps/s. Throughput plateaus after ~4096. |
| Contact / collision performance | **Loses badly.** Rapier is ~26× faster on an 8-box stack. |
| "Analytical derivatives for free" | **Not free; not the same class as finite differences either.** A gradient rollout costs 6–9× a forward rollout per DOF, and that ratio is flat in parameter count — 160 parameters at one DOF costs 9.2×, the same as 10 parameters. So it beats finite differences by a margin that grows with parameter count (3.0× at 10 parameters, 18.3× at 80, measured) and loses to textbook reverse mode's small constant. "Free" is wrong; "the same scaling as finite differences", which this table said until the `adjoint scaling` suite tested it, was also wrong. |
| Numerical quality | **Holds.** Energy error falls as O(dt) exactly as a symplectic integrator should, on both a simple and a chaotic scene. |

Detail, settings, and caveats below. **Read the caveats before quoting a
number** — particularly for the contact comparison, where the two engines are
not running the same algorithm and cannot be made to.

## Methodology

### Measurement protocol

Identical for every engine, which is the only way a cross-library number means
anything:

| | |
|---|---|
| Warmup | 2 repetitions, discarded |
| Timed repetitions | 7 |
| Work per repetition | 20 000 steps (single-sim and comparison suites) |
| Statistic | **Median** of the 7, chosen for robustness to a scheduler hiccup |
| Also reported | min, max, and spread `(max−min)/median` |
| Build | `--release`, no `target-cpu=native` unless recorded in the run metadata |

Every repetition resets the scene to its initial state inside the timed
closure, so repetition 7 simulates the same trajectory as repetition 1. The
Rapier world is rebuilt per repetition, because Rapier puts settled islands to
sleep and reusing a world would flatter it.

### Honesty mechanisms

Enforced by the harness, not by good intentions:

- **Spread is published, and noise is flagged.** Any row over 25% spread is
  marked ⚠ and triggers a per-suite warning. Do not quote a ⚠ row.
- **Instability cannot masquerade as speed.** Every timed scene is checked for
  a finite final state, because a diverged simulation does *less* work per
  step. Every row carries a `stable` metric.
- **Debug builds are labelled invalid** in the run metadata and warned about at
  startup.
- **Skips are recorded with reasons**, never silently omitted.
- **The gradient suite cross-checks itself** against finite differences
  (`adjoint_vs_fd_max_rel_err`). A fast gradient that disagrees with FD is not
  a result.

### Physics settings

Single source of truth:
[`crates/phyz-bench/src/settings.rs`](crates/phyz-bench/src/settings.rs). Every
JSON record embeds the full settings block it was measured under.

| Setting | Articulated scenes | Contact scenes |
|---|---|---|
| Timestep | 1 ms | 2 ms |
| Gravity | `(0, 0, −9.81)` m/s² | same |
| Solver iterations | 4 (inert for phyz — it has no velocity solver) | 4 |
| Contact stiffness | — | 1×10⁵ N/m |
| Contact damping | — | 1×10³ N·s/m |
| Friction | — | 0.5 |
| Restitution | — | 0.0 |

### Scenes

| Scene | Definition |
|---|---|
| `pendulum` | 1 revolute link, 1 m, 1 kg, thin-rod inertia, hinged about **+Y**, released at 1.0 rad |
| `double_pendulum` | 2 such links, released at (1.0, 0.5) rad — chaotic, so it tests the integrator rather than a closed form |
| `ant` | `models/ant.xml` via the MJCF loader: free-floating torso + 8 hinges, 14 DOF |
| `box_stack_8` | 8 free 10 cm cubes, 1 kg each, 1 cm initial gaps, on a ground plane |

The hinge axis is +Y, not phyz's default +Z. With a rod hanging along −Z under
−Z gravity, a Z hinge puts the centre of mass *on* the rotation axis: the
gravitational torque is identically zero and the "pendulum" never moves. (The
pre-existing benchmark in `crates/phyz-diff/benches/jacobians.rs` has this
problem and is benchmarking a stationary body.)

### What phyz's "step" means here

phyz ships no `Simulator` facade, so the benchmark loop is assembled from the
public pieces a user would reach for:

```
forward_kinematics  →  (ground + pairwise contact)  →  aba_with_external_forces  →  semi-implicit Euler
```

Contact scenes run **both** contact paths — the ground-plane query and
sweep-and-prune + GJK/EPA between boxes — so the measured cost includes
narrow-phase collision, as Rapier's does.

## Cross-library comparison

### Rapier

`rapier3d-f64` 0.34, in-process, no FFI in the measurement.

**Built as f64 deliberately**, to match phyz's precision. Stock `rapier3d` is
f32 and would likely be faster than the numbers here. That choice is documented
rather than exploited in either direction.

What is held equal: timestep, gravity, masses, inertia tensors, link lengths,
initial angles, friction coefficient, restitution, solver-iteration request.

**What cannot be held equal:**

- **The pendulums are close to like-for-like.** Rapier's multibody joint set is
  reduced-coordinate, like phyz's ABA. This is a fair fight.
- **The box stack is not a controlled experiment.** phyz uses a compliant
  penalty force (stiffness/damping); Rapier uses an impulse solver with
  penetration slop. There is no setting that makes these the same algorithm.
  Only friction and restitution translate. Read that row as "cost of each
  engine's own contact story on the same scene at the same timestep".
- **The ant has no Rapier row.** It is loaded from MJCF, which Rapier does not
  parse in-tree. Hand-building it would risk an unequal model, so no comparison
  is published rather than a bad one.
- **`solver_iterations = 4` equalises what we asked for, not the arithmetic
  performed.** phyz has no velocity solver at all.

### MuJoCo / MJX

A separate, optional Python harness:
[`crates/phyz-bench/python/`](crates/phyz-bench/python/). Deliberately **not** a
CI dependency and not part of `make bench` — MuJoCo needs a Python environment
and MJX needs JAX plus a GPU to be worth running, and making either mandatory
would put the benchmark suite out of reach for most people.

It emits the same JSON schema, so results merge into one document. See that
directory's README for the full caveat list; the load-bearing ones are that
MuJoCo's soft-constraint contact is a third distinct algorithm, that Python FFI
overhead is material for the pendulum scene specifically, and that MJX is f32.

## Interpretation

### Where phyz wins

**Reduced-coordinate articulated dynamics.** phyz's ABA edges out Rapier's
multibody solver on the pendulum scenes at matched precision — 1.08× and 1.02×.
That is a narrow win, and small enough that on another machine it could go the
other way; the honest reading is "competitive", not "faster". For
robotics-shaped problems — a kinematic tree, few or no contacts — this is
phyz's strong suit, and 229 k steps/s on a 14-DOF ant is a genuinely useful
number: 229× real time at a 1 ms timestep.

**Batched GPU rollouts, at scale.** Above batch ~128 the GPU path pulls away,
reaching ~36× a CPU thread at batch 4096 and 7.8 M environment-steps/s at
16 384 environments. "Thousands of parallel environments" is substantiated.

### Where phyz loses

**Contact, by a lot.** Rapier is ~26× faster on an 8-box stack. Some of that is
algorithmic (an impulse solver on a settled stack does very little work; a
penalty model integrates the same forces every step regardless), and some is
that phyz's broad/narrow phase is not optimised. Either way, if your workload
is contact-dominated, the numbers say use Rapier.

**Small-batch GPU.** At batch 1 the GPU path is ~100× *slower* than one CPU
thread, and it does not break even until batch ~128. The crossover is the
number that matters, and it should be in the README next to the word
"GPU-accelerated". Throughput also plateaus between 4096 and 16 384, so the
last 4× in batch size buys ~1.1× in throughput.

**Gradients — expensive, but not for the reason this document used to give.**

An earlier revision of this section read the gradient suite's two rows — 18×
the forward pass at 10 parameters, 45× at 20 — and concluded that the adjoint
costs a lane per parameter, putting it in finite differences' asymptotic class.
That conclusion was wrong, and it was wrong because two scenes cannot support
it. The pendulum has one body, one DOF and ten parameters; the double pendulum
has two of each. Parameter count and DOF count move together, so those rows are
equally consistent with either explanation.

The `adjoint scaling` suite separates them. `weld_chain_N` hangs `N` rigidly
welded bodies off a single revolute joint: every welded body carries a full
ten-parameter spatial inertia and is dynamically live, but a `Fixed` joint adds
no DOF, so the parameter count grows 16× while `nv` stays at 1. `dof_chain_N`
is the control, growing both together as the gradient suite's scenes do.

The tables below come from `phyz-bench --suite adjoint-scaling` on a **different
host** from the generated results above, so do not compare their absolute
milliseconds against that section. Every column here is a ratio between two
quantities measured back to back on the same machine, which is what the
argument rests on; re-run `make bench` on the publishing host to fold them into
the generated block.

| family | parameters | nv | adjoint ratio | ratio ÷ parameters | ratio ÷ DOF |
|---|---|---|---|---|---|
| `weld_chain_1` | 10 | 1 | 6.9× | 0.685 | 6.9 |
| `weld_chain_4` | 40 | 1 | 8.1× | 0.203 | 8.1 |
| `weld_chain_16` | 160 | 1 | **9.2×** | **0.057** | 9.2 |
| `dof_chain_1` | 10 | 1 | 6.4× | 0.638 | 6.4 |
| `dof_chain_4` | 40 | 4 | 22.3× | 0.557 | 5.6 |
| `dof_chain_16` | 160 | 16 | **97.6×** | 0.610 | **6.1** |

Sixteen-fold more parameters at fixed DOF costs 33% more time. Sixteen-fold
more DOFs costs 15× more. The `ratio ÷ DOF` column is flat at 5.6–6.4 across
the entire sweep — **the adjoint's cost is linear in DOF count and very nearly
independent of parameter count**, which is what the implementation says it
should be: the parameter and contact channels ride two `O(nb)` sweeps, while
the *state* Jacobian costs `nq + nv` dual-ABA lanes per step.

That changes the comparison against finite differences, which the earlier
reading got backwards. At fixed DOF count, FD costs `2·n_params` rollouts and
the adjoint does not, so the adjoint's advantage grows with the parameter count
— measured, not projected:

| parameters (nv = 1) | adjoint | finite differences | adjoint speedup |
|---|---|---|---|
| 10 | 6.9× fwd | 20.5× fwd | **3.0×** |
| 20 | 7.6× fwd | 39.4× fwd | **5.2×** |
| 40 | 8.1× fwd | 81.2× fwd | **10.0×** |
| 80 | 8.7× fwd | 158.9× fwd | **18.3×** |

The gradient suite's near-unity `adjoint_speedup_vs_fd` was never evidence of a
bad asymptotic — it is what you get when a model has ten parameters per DOF and
only one or two DOFs, so the adjoint's constant factor has nothing to amortise
against. On a real system-identification problem, where parameters outnumber
DOFs, the adjoint wins by the margin above and keeps widening.

**What is still true, and what the remaining cost is.** 6–9× the forward pass
for a single-DOF model is a large constant, and it is *not* the ~2–4× textbook
reverse mode delivers. The residual is the state Jacobian: `nq + nv` separately
seeded dual passes through ABA per timestep, each re-walking the kinematic tree
to extract one column. Vector-mode duals — one pass carrying all `nq + nv`
directions — would amortise that traversal, and that is the optimisation to
make next. The parameter channel needs no work; it is already asymptotically
right.

And exactness stands on its own: `adjoint_vs_fd_max_rel_err` ≈ 1e-10 with no
step size to choose and no truncation or cancellation error.

There is also a scope limit worth stating: the differentiable rollout requires
`nq == nv` and single-DOF joints, so the ant — anything with a free-floating
base — cannot be differentiated at all today.

### Numerical quality

Energy error falls as O(dt) on both the simple and the chaotic pendulum over a
5 s horizon — exactly what a first-order symplectic integrator should do:

| dt | pendulum peak error | double pendulum peak error |
|---|---|---|
| 4×10⁻³ | 6.2×10⁻³ | 5.1×10⁻² |
| 2×10⁻³ | 3.1×10⁻³ | 2.6×10⁻² |
| 1×10⁻³ | 1.5×10⁻³ | 1.3×10⁻² |
| 2.5×10⁻⁴ | 3.9×10⁻⁴ | 3.3×10⁻³ |

Every 4× reduction in `dt` gives a 4× reduction in error, across a 16× range.
The integrator is correct.

Over a 100 s horizon the double pendulum's energy error stops responding to
`dt` entirely. That is not an integrator bug — it is chaos. By 100 s the
rollout has diverged onto a neighbouring trajectory and the energy band is set
by the horizon, not the timestep. The practical consequence: on a chaotic
system, buying accuracy with a smaller `dt` works on short horizons and stops
working on long ones. Both horizons are reported so the distinction is visible
rather than inferred.

## Reproducing and publishing

```bash
make bench          # -> bench-results.json, bench-results.md
make bench-gpu      # adds the GPU sweep
```

`bench-results.json` is the machine-readable artifact
(`schema_version: 1`, see [`report.rs`](crates/phyz-bench/src/report.rs)),
suitable for tracking over time and rendering on phyz.dev. Its `meta` block
carries hardware, OS, rustc version, library versions, and git commit — every
published number must travel with those.

### CI

The [`bench` workflow](.github/workflows/bench.yml) is **not** wired into the
main gate. It runs on manual dispatch and weekly, `continue-on-error`, purely
to prove the harness still runs and to produce an artifact. Timing numbers from
shared GitHub runners are noise, and a gate built on noise is one people learn
to ignore. Its output is stamped with a banner saying it is not a published
result.

Publishable numbers come from a known, idle machine, recorded by hand with
`make bench`.

### A note on the host

Benchmarking on a busy machine produces fiction. The spread column and the ⚠
flags exist so that fiction is visible when it happens. If you see ⚠ rows,
re-run on an idle host before believing them.
